# Router Module

This module utilizes [Hermes](../../libraries/hermes) so as to expose application-level APIs and
provide a way for Conduit modules to register application routes.

## Features ✔️

- REST (with Swagger)
- GraphQL
- WebSockets (via Socket.io)

## Requirements ⚡

- [Database](../database) module

## Environment Variables 📃 <a name="env-vars"></a>

|       Variable       | Description                                          | Required |      Example       |
|:--------------------:|:-----------------------------------------------------| :------: |:------------------:|
|   `CONDUIT_SERVER`   | Conduit Core's address and port                      |   True   |  `0.0.0.0:55152`   |
|     `SERVICE_URL`    | This should be where this service listens on. If behind a LB it should point to the LB's IP/DNS  |   False   |  `0.0.0.0:55190`   |
|     `GRPC_PORT`      | The port number the gRPC server will listen to                      |  False   |  `55190`           |
|     `GRPC_KEY`       | Specifying a secret enables gRPC signed request protection (**use across modules**) |   False  | `someRandomSecret` |
|  `CLIENT_HTTP_PORT`  | Port to be used by application REST and GrahpQL APIs |  False   |  `3000` |
| `CLIENT_SOCKET_PORT` | DPort to be used by application WebSockets API       |  False   |  `3001` |

Module settings that are not process environment variables live in the convict schema (`src/config/config.ts`). Production sets them through the Admin API, `PATCH /config/router`, the same route Core registers for every module.

`security.clientSecretEncryptionKey` is standard base64 of 32 bytes (44 characters, ending in `=`). Generate it with `node -e "process.stdout.write(require('node:crypto').randomBytes(32).toString('base64'))"`. `CLIENT_SECRET_ENCRYPTION_KEY` is read when a client is created or a signature is checked. It is not written into the stored config. If that environment variable is a non-empty string, it wins over the stored value, so a PATCH made while the variable is set does not change what verification uses and is not a rotation.

```json
{
  "config": {
    "security": {
      "clientValidation": true,
      "clientSecretEncryptionKey": "<base64 of 32 bytes>",
      "clientSignaturePathPrefix": "/api"
    }
  }
}
```

A later GET returns `[REDACTED]` for the key. Sending `[REDACTED]` back keeps the stored key when a real key is already stored. When nothing is stored, `[REDACTED]` is treated as empty and is not saved. An empty key does not stop startup. With validation on and no usable key, the process logs a warning and non-web clients get 401. Web clients still use the origin check.

The HMAC key is the 43-character `base64url` secret from `POST /router/security/client`, used as UTF-8. It is not base64-decoded. It is not the encryption key. Payload lines, joined by `\n`: timestamp string, method uppercased, signed path, hex SHA-256 of the body.

The HTTP signed path is `clientSignaturePathPrefix` plus the path and query the router sees (`originalUrl`). Example: the client calls `/api/users?limit=1`, the proxy strips `/api`, the prefix is `/api`, the router sees `/users?limit=1`, and the signed path is `/api/users?limit=1`. The prefix is stored exactly as sent. `/api/` plus `/users` is `/api//users` and will not match. The body hash is the buffer `captureRequestRawBody` stores. `express.json`, `urlencoded`, and `raw` call `verify` after body-parser inflates `Content-Encoding`. Hash those bytes. No body hashes the empty buffer `e3b0c44298fc1c149afbf4c8996fb92427ae41e4649b934ca495991b7852b855`.

Sockets: only the handshake is checked. Follow-up requests that carry `sid` are not checked again, so a long-poll can run longer than 3 minutes. The signed path is `req.path` with no query. For the server's `path: '/realtime'`, that value is `/realtime/` (plus the prefix if set). That is the engine path, not the socket.io namespace (`/events/` or `/database/`). Method is `GET`. Body hash is the empty-body hash. A failed handshake is engine.io HTTP 400. REST signature failures stay HTTP 401.

Reconnects are new handshakes. The client must build a new timestamp and signature before each attempt. `extraHeaders` stay fixed until the process replaces them. Example (Node, default polling then upgrade):

```javascript
import { io } from 'socket.io-client';
import { createHmac, createHash } from 'node:crypto';

const secret = process.env.CLIENT_SECRET; // 43-character secret, UTF-8, not base64-decoded
const prefix = ''; // security.clientSignaturePathPrefix
const signedPath = `${prefix}/realtime/`;

function authHeaders() {
  const timestamp = Date.now().toString();
  const bodyHash = createHash('sha256').update(Buffer.alloc(0)).digest('hex');
  const payload = [timestamp, 'GET', signedPath, bodyHash].join('\n');
  const signature = createHmac('sha256', secret).update(payload, 'utf8').digest('hex');
  return {
    clientid: process.env.CLIENT_ID,
    'x-conduit-timestamp': timestamp,
    'x-conduit-signature': signature,
  };
}

const socket = io(`${process.env.SOCKET_URL}/events/`, {
  path: '/realtime',
  extraHeaders: authHeaders(),
});

socket.io.on('reconnect_attempt', () => {
  socket.io.opts.extraHeaders = authHeaders();
});
```

A client that retries a failed HTTP request must sign it again. The first signature is consumed for 3 minutes even when the application returned an error after the signature matched.

Changing `clientSecretEncryptionKey` makes every stored secret fail decryption. Every non-web client must be recreated. There is no rotation. Web clients keep working on origin. Existing bcrypt secrets cannot be verified. Recreate those clients.

With validation on, these cannot sign a fresh request, and there is no second credential:

- MCP at `/mcp` (Express client middleware runs before the `/mcp` handler)
- Swagger "try it" (the scheme is already the three signature headers; the UI cannot compute the HMAC)
- Postman and other fixed-header collections
- Uptime monitors

Still exempt, unchanged: paths starting with `/hook`, `/`, `/ready`, and `GET` `/graphql`, `/swagger`, and `/reference` when not in production. A fake `sid` is dropped by Engine.IO after the client middleware and never becomes a namespace connection or a REST route.

## Usage

The router, as all modules in Conduit, communicates through the [gRPC-sdk](../../libraries/grpc-sdk).

For every route that you declare you have the following parameters:

- input: ConduitRouteOptions,
- type: ConduitRouteReturnDefinition,
- handler: (request: ConduitRouteParameters) => Promise

Let's break them down to see what they do

### Input

These options specify the parameters that Conduit should extract
from the requests of the clients. Each field represents a different
position in the request. It mainly effects REST requests, since GraphQL
only has one type of parameter. Parameters default to optional if the required
field is missing.

- queryParams?: ConduitRouteOption;
- bodyParams?: ConduitModel;
- urlParams?: ConduitRouteOption;

Actions are GET, PUT, POST, DELETE. While these verbs are more obvious in REST,
on GraphQL they are used to distinct between queries(GET) and mutations(the rest). Also,
they are used to provide more descriptive naming when query names are not provided by the user
or if the endpoints are auto-generated like in the case of the CMS.

- action:ConduitRouteActions;

The path field is used for REST urls and for the auto-generated names of GraphQL.

- path: string;

The name for the route is optional and only used in GraphQL currently. If you
do not wish for conduit to generate the GraphQL names then you can specify your name here.
- name?: string;

Description isn't currently used, but will be added in Swagger and GraphQL to provide more info on the specific route
- description?: string;

Middlewares specify each middleware that should be run before the actual handler that you provide.
The middlewares array should contain names of handlers that conduit knows about.
In the future this may also include external urls.
- middlewares?: string[];

The cacheControl field works almost the same as the relevant HTTP header.
It expects either public,max-age=number or private,max-age=number or nothing.
If you sent any other string that those provided conduit will not utilize caching for the request.
The number that you specify also sets the expiry time of conduit's cache. All caching takes place,
AFTER middleware execution
- cacheControl?: string;

## Event Relays

Event Relays map an **exact** Redis bus channel to a Socket.io event on the dedicated `/events/` namespace.
They are configured through the Admin API (`/router/event-relays`) and are **ephemeral**: Redis pub/sub is not replayed, and missed events are not stored.

Each relay stores a ReBAC check (`permission` on `resourceType:resourceId`). Clients never choose a raw room name. Optional `notes` describe the relay for operators.

### Client contract

```javascript
import { io } from 'socket.io-client';

const socket = io(`${SOCKET_BASE_URL}/events/`, {
  path: '/realtime',
  auth: { token: accessToken },
});

socket.on('connect', () => {
  socket.emit('subscribe', relayId, resourceId);
});
socket.on('order-updated', payload => {
  // payload is the rendered JSON template
});
socket.emit('unsubscribe', relayId, resourceId);
```

- Subscribe is allowed only when `User:<id>` has the relay `permission` on `<resourceType>:<resourceId>`.
- The outbound event name is the relay `socketEvent`.
- Placeholders in `messageTemplate` use `{{payload.path}}` against the bus JSON payload.

**Subscribe-only.** Clients cannot publish on `/events/`; modules publish to the Redis bus and relays forward matching messages to subscribed rooms.

**Authentication and Authorization** are required (`authMiddleware` on subscribe). Authorization is re-checked on a short TTL during delivery; revoked access triggers `leave-room`.

**Rooms** are server-assigned: `er:<relayId>:<sha256(resourceId)>`. Conduit has no tenant model and **team ids are not part of room names** — isolation is ReBAC on `User` × `permission` × `resourceType:resourceId`.

**HA / `localOnly`:** every Router replica subscribes to the bus and emits with `localOnly`, so clients spread across replicas still receive one copy without sticky sessions for delivery. Engine.IO **polling** transport still benefits from sticky sessions or WebSocket-only clients.

**EventBus self-publish:** the bus ignores this process’s own publishes (signature filter). A relay on a channel the Router publishes will not deliver to local clients for those self-originated messages (typical for module-originated events).

**Dual delivery warning:** Database `/database/` `change` events and a relay on overlapping bus channels (for example `database:change:*` or CRUD `database:update:*`) can duplicate notifications. CRUD bus payloads include **full documents** — prefer change-stream style payloads when both paths are enabled.

Use preview to validate templates: `POST /router/event-relays/preview` with `messageTemplate` and `samplePayload` (same renderer as runtime; sample JSON is capped at 256 KiB like inbound bus payloads).
